# cal-todo PRD (초안)

> 기준 문서: [도메인 정의서](1-domain-definition.md). FR/BR ID는 도메인 정의서와 동일하며, 상세 규칙·정의는 해당 문서를 따른다.

## 1. 개요·목표
- 개요: 인증된 사용자가 개인별로 할일을 관리하고, 시작일·종료일 기준으로 목록과 월별 캘린더에서 조회하는 할일관리 웹앱 (도메인 정의서 §1~2).
- 비즈니스 목표: 1000명이 동시 접속하여 사용할 수 있어야 한다.
- KPI: 이번 범위 외

## 2. 목표 사용자
- 학생 및 20~50대 직장인
- 페르소나·상세 시나리오: 생략

## 3. 범위
- 포함: FR-01 ~ FR-08 (카테고리 생성·수정·삭제, 완료 처리 토글, 삭제 전 확인 포함), 화면 다국어 표시(한국어·영어, 8-plan FE-15), 다크/라이트 모드 전환(8-plan FE-16)
- 제외: 비밀번호 정책 등 비기능 요구 (도메인 정의서 §5), 접근성, 모바일 전용 UI(반응형 웹만 적용), KPI·성능 기준·배포·로깅, 동시접속 부하 테스트

## 4. 기능 요구사항
규칙은 도메인 정의서 §4 BR-xx, 상태 판단은 §3 '할일 상태'를 따른다.

| ID | 기능 | 수용 기준 | 관련 규칙 |
|---|---|---|---|
| FR-01 | 회원가입 / 로그인 | 가입 후 자동 로그인하지 않고 로그인해야 앱 사용 가능. 이메일은 대소문자 구분 없이 유일하며 중복 이메일은 가입 불가 및 오류 안내. 로그인 실패 시 이메일/비밀번호 구분 없이 "이메일 또는 비밀번호가 올바르지 않습니다." 안내. 미인증 접근 시 로그인 화면으로 이동 | BR-01, BR-07 |
| FR-02 | 내 정보 수정 | 로그인 사용자가 본인 정보 중 이름만 수정할 수 있다 (이메일·비밀번호 변경 불가) | BR-01 |
| FR-03 | 할일 등록 | 카테고리 미지정 시 '기본' 적용. 시작일 기본값은 일주일 후, 종료일 기본값은 시작일과 동일. 날짜는 캘린더로 선택. 종료일 < 시작일이면 저장 불가 및 오류 안내 | BR-01, BR-03~06 |
| FR-04 | 할일 수정, 완료 처리 | 편집 화면에서 수정 가능(완료 입력은 편집 화면에 두지 않음). 본인 할일만 수정 가능. 날짜 검증은 등록과 동일. 목록 체크박스로 완료를 토글하며 완료 후에도 미완료로 되돌릴 수 있다 | BR-02, BR-04, BR-06, BR-12 |
| FR-05 | 할일 삭제 | 삭제 전 브라우저 기본 확인창을 1회 표시. 본인 할일만 삭제 가능. 타인 할일 요청은 거부되고 데이터 변경 없음 | BR-02 |
| FR-06 | 할일 조회 | 목록과 월별 캘린더를 탭으로 전환. 본인 할일만 표시. 캘린더는 필터 없이 시작일~종료일의 각 날짜에 제목을 표시하며 클릭 동작은 없다 | BR-02 |
| FR-07 | 할일 목록 필터링 | 카테고리·상태(시작 전/진행중/완료/기한 초과) 필터 제공. 카테고리 + 상태 1개 AND 적용. 상태는 KST 오늘 기준. 결과가 없으면 "조건에 맞는 할일이 없습니다." 표시 | BR-02, BR-08 |
| FR-08 | 카테고리 관리 | 로그인 사용자가 본인 카테고리를 생성·수정·삭제할 수 있다. '기본' 카테고리는 가입 시 사용자별로 생성되며 수정·삭제할 수 없다(400, 데이터 변경 없음). 이름은 비어 있을 수 없고(400) 사용자별로 유일하다(409). 삭제 전 브라우저 기본 확인창을 1회 표시. 카테고리를 삭제하면 해당 카테고리의 할일은 '기본' 카테고리로 변경된다 (할일은 삭제되지 않음) | BR-01, BR-03, BR-09, BR-10, BR-11 |

## 5. 비기능 요구
- 동시 접속: 1000명은 목표로 유지하되 이번 범위에서 부하 테스트는 하지 않는다
- 그 외 성능 수치(응답시간 등): 이번 범위 외

## 6. 기술 제약
| 구분 | 내용 |
|---|---|
| 플랫폼 | 웹 우선, 모바일은 반응형 웹 UI로만 고려 |
| 프론트엔드 | React 19 + TypeScript + Zustand + TanStack Query |
| 서버 상태 | TanStack Query (API 데이터 조회·캐싱·갱신) |
| 클라이언트 상태 | Zustand (UI 상태 등 서버와 무관한 상태) |
| 백엔드 | Node.js + JavaScript + Express + pg 라이브러리 (Prisma 사용 금지) |
| 데이터베이스 | PostgreSQL 17 |
| 인증 | JWT 기반. Access Token + Refresh Token 사용 |

### 구성도
```
[브라우저: 반응형 웹]            [서버]                      [DB]
 React 19 + TypeScript   REST   Node.js + Express    pg     PostgreSQL 17
 - Zustand (클라이언트 상태) <----> - API, JWT 검증  <----->
 - TanStack Query (서버 상태)
```

### 인증 방식 (JWT: Access Token + Refresh Token)
1. 로그인 성공 시 서버가 Access Token(15분)과 Refresh Token(7일)을 발급한다.
2. 클라이언트는 두 토큰을 localStorage에 저장하고, API 요청마다 Access Token을 보내면 서버는 이를 검증한다.
3. Access Token이 만료되면 Refresh Token으로 새 Access Token을 발급받는다.
4. Refresh Token도 만료되었거나 유효하지 않으면 로그인 화면으로 이동한다. (BR-01)
5. Refresh Token은 서버에 저장·폐기하지 않는다(서버 무상태). 로그아웃은 클라이언트의 토큰 삭제로 처리한다.

## 7. 프로젝트 관리
- 일정: 2일 내 핵심 기능 완성
- 팀: 1인 개발
- 예산: 1인 개발에 준하는 예산

## 8. UX 원칙
- 반응형 웹 UI만 적용 (모바일 우선 설계는 하지 않음)
- 접근성: 이 앱에서는 고려하지 않음
- 다국어: 화면 문구는 한국어·영어를 지원하고 사용자가 선택한 언어를 유지한다. 사용자가 입력한 데이터(할일 제목, 카테고리 이름)는 번역하지 않는다
- 다크/라이트 모드: 처음에는 OS 설정을 따르고, 사용자가 전환하면 선택한 모드를 유지한다

## 9. 결정 사항
도메인 정의서 §7 항목을 이어서 기록한다. 남은 미결 사항은 없다.

| 항목 | 결정 |
|---|---|
| 카테고리 소유 범위 | 사용자별 (관리 기능은 FR-08로 범위 포함) |
| '기본' 카테고리의 수정·삭제 가능 여부 | 불가 (BR-10) |
| 상태 판단 시간대 | KST |
| 필터 조합 방식 | 카테고리 + 상태 1개 AND |
| 완료 처리 되돌림 가능 여부 | 가능 (BR-12) |
| 여러 날에 걸친 할일의 캘린더 표시 방식 | 시작일~종료일 각 날짜에 표시, 필터·클릭 동작 없음 |
| 삭제 시 확인 절차 | 할일·카테고리 삭제 전 브라우저 기본 확인창 1회 |
| KPI 수치, 동시접속 외 성능 기준 | 이번 범위 외 |
| 배포·로깅·모니터링 | 이번 범위 외 |
| 토큰 만료 시간, 토큰 저장 위치 | Access Token 15분 / Refresh Token 7일, localStorage |
| Refresh Token 서버 저장·로그아웃 | 서버 무상태, 로그아웃은 클라이언트 토큰 삭제 |
| 동시접속 1000명 검증 | 목표로만 유지, 부하 테스트 하지 않음 |
| 다국어 지원 범위 | 한국어(기본)·영어. 화면 문구만 번역하고 서버 오류는 `error.code`로 프론트에서 번역. 백엔드 변경 없음 (8-plan FE-15) |
| 다크/라이트 모드 | 프론트에서만 처리. 초기값은 OS 설정, 전환 시 localStorage 유지 (8-plan FE-16) |
